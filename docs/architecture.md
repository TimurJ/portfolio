# Architecture

A one-page static site: Astro renders everything to HTML at build time, and the client ships no framework — just a few small vanilla scripts, each owned by the component whose markup it drives. There is no adapter and no server code; the output deploys as static assets (see [deploying.md](deploying.md)). Rendering fidelity is specified by the design file, not by this doc (see [design.md](design.md)).

## Layout

```
src/
  pages/index.astro       The page: assembles the layout, header, and sections
  pages/404.astro         Error page: Base + a way back home (noindex)
  pages/robots.txt.ts     Generated robots.txt, pointing at the sitemap
  layouts/Base.astro      <head>, fonts, and the pre-paint theme script
  components/
    Header.astro          Sticky nav; owns --headerH and the active-link highlight
    ThemeToggle.astro     Light/dark switch
    Section.astro         Shared list-section shell (intro, row list, scroll cue)
    SectionIntro.astro    Shared section header (eyebrow, title, blurb, CTA slot)
    ContactCta.astro      Shared "Get in Touch" mailto (header + section intros)
    ScrollCue.astro       Shared "Scroll down" link (each section's cue)
    DotLabel.astro        Shared dot-and-label mark (intro eyebrows, row meta)
    Hero.astro            Page section
    Experience.astro      Page section
    Blog.astro            Page section
    Contact.astro         Page section (contact CTA)
    Footer.astro          Site footer; owns --footerH
  styles/global.css       Design tokens, Tailwind setup, base styles
  lib/theme.ts            Theme storage-key / attribute constants
  lib/nav.ts              Section order, ids, and labels (the single source)
  lib/site.ts             Site identity: email, name, role, socials (page title, Hero, Contact, Footer, Base's JSON-LD)
  lib/icons.ts            Shared presentation attrs for inline stroke icons
  assets/                 Images processed by astro:assets
tests/site.spec.ts        Playwright smoke suite + axe scan, run against dist/
playwright.config.ts      One chromium project; serves dist/ on port 4322
public/                   Files served verbatim (favicons, _headers, og.jpg)
scripts/og-card.html      Source for public/og.jpg — rendered once at 1200×630, not built
scripts/rasterize-favicon.mjs  Regenerates favicon.ico + apple-touch-icon.png from favicon.svg
```

## Page composition

`index.astro` is the only content page (`404.astro` is a chrome-less error page: `Base` + a way back home, served by the Worker via `not_found_handling: "404-page"`, and the one page that passes `Base`'s `noindex` — it ships as a directly reachable static asset, so it takes a `robots` directive instead of a canonical). It composes `Base` → `Header` → one component per page section, in scroll order. Section order itself lives once, in `lib/nav.ts` (`sections`): the header and footer navs render it, and each section declares its own `id` as a typed `SectionId` against it (the two list sections hand theirs to `Section`) — so a renamed or reordered section is a type error, not a dead link. The scroll-cue chain is walked there too rather than wired up by the page: `nextOf(id)` returns the next section's link target, so a section derives its own cue from its own id and `index.astro` composes the sections in order and passes nothing. `nextOf` returns `undefined` for the last section — `noUncheckedIndexedAccess` forces that, and it is the honest type anyway — so `Section` and `Hero` render the cue only when there is one, and a section that becomes last stops cueing instead of pointing nowhere. `titleIdOf` sits beside `hrefOf` for the same reason: a `<section>` is exposed as a `region` landmark only once it has an accessible name, so every section points `aria-labelledby` at its own heading, and both the id and the reference are derived from the one `SectionId`. `titleIdOf` is annotated to return the four-member union `` `${SectionId}-title` `` rather than widening to `string`, and `SectionIntro`'s `titleId` prop is typed to it — otherwise any string would satisfy the prop and the derivation would buy nothing from the compiler, which is the whole point of deriving it. It is deliberately not generic in the section id: no consumer holds one section's title id at a type narrower than that union, so the extra precision would be computed and discarded. `SectionIntro` therefore takes `titleId` as a _required_ prop — an unnamed section is a silent accessibility regression, so it is a type error instead — while `Section` derives it from the section id rather than asking its consumer for it. The chain ends at Contact, which composes `SectionIntro` directly and carries no scroll cue; the site footer (`Footer`) follows as a sibling _after_ `<main>`, because a `<footer>` nested in `<main>` (or any section) loses its `contentinfo` landmark role. Inside it, each link column names itself from its own visible heading: the Navigate column is a second `<nav>` (labelled, so it is distinguishable from Header's) and the Elsewhere column a `role="group"`, since profile links are not site navigation. Without that the six links arrive in `contentinfo` as one undifferentiated run, with the headings that explain them related only by position — and no axe rule covers it, so the structure is the only thing carrying the grouping.

Ownership boundaries:

- **`Base.astro`** owns the document: metadata, the Fonts API setup, and the inline pre-paint script — which resolves the theme and raises the `data-js` flag, the two things that have to be settled before the first paint rather than after it.
- **`Header.astro`** owns everything header-shaped: the nav (it renders the shared `lib/nav.ts` sections — the highlight script still skips links whose section doesn't exist), the measured `--headerH` custom property that `section-screen` heights and the anchor-scroll offset depend on, the scroll-driven active-link highlight, and the skip link. The skip link ships here rather than in `Base` because it exists to skip the nav: `404.astro` has no chrome, so a skip link there would be a focusable no-op pointing at the only thing on the page. The cost is one contract with the consuming page — `index.astro`'s `<main>` carries `id="main"`, and both ends say so.
- **Section components** are self-contained: markup, section-scoped styles, behavior, and content live in one file. Section content is a typed const in the component's frontmatter — with a single consumer and a handful of entries, colocated data beats indirection. Content collections are reserved for genuinely repeating content (future blog article pages — the homepage blog section is a typed const like every other section).
- **Shared components** are extracted only when duplication is proven in the design source, not anticipated. `SectionIntro` exists because the Experiences and Blog intros are identical in the design down to their responsive tiers — and Contact consumes it too, as the `closer` variant (roomier padding, centered aside, its own tier steps) with its mailto button passed through the named `cta` slot in place of the default `ContactCta`; `Section` because those same two sections open with a byte-identical shell (intro → `section-list` of rows → `section-cue`), so they now supply only their rows through its slot, with the intro props picked off `SectionIntro`'s own type (`ComponentProps`) so the two can't drift; `ContactCta` because the header and section intros carry the same CTA; `ScrollCue` because every section ends in the same cue; `DotLabel` because the design's dot-and-label mark is the same in the row meta and, one size up, in every intro eyebrow. Contact takes none of the shell — no row list, no cue — so it keeps composing `SectionIntro` directly.

Per-consumer variation enters through props and slots (e.g. `condensed`, `closer`, `compact`, `class`, the `cta` slot), never by reaching into the component from outside. The default `scopedStyleStrategy` doesn't carry a parent's scope into a child component, so a scoped class name passed inward would never match the rule that named it. Two consequences run through the shared components: placement styling (`.hero-scroll`) lives on a wrapper the consumer owns; and where the override would have to land _inside_ a shared component it becomes a prop instead — `Section`'s `condensed` tightens the intro and the closing cue together, for a section that must fit one small-phone screen (the cue's share lives with the `section-cue` utility in `global.css`, keyed off a `data-condensed` attribute, so the cue's whole padding ladder stays in one place and `Section` ships no styles of its own), and `ContactCta`'s `compact` drops the CTA entirely below the phone-sm tier, for the header's tight row, where the section intros keep showing it. Below 460px the header cannot hold the nav and the CTA on one line: the nav sits in a `minmax(0,1fr)` column, so it overflows under the actions column and the theme toggle lands on top of the Contact link. Hiding the CTA is what keeps the header one line rather than growing it to two — the Experience and Blog intros carry the same CTA twice more, the Contact section repeats it as a filled button, and the nav's own Contact link is right there. The rule has to live inside the component: Astro gives the anchor `ContactCta`'s own scope id, so a rule written in `Header` could not select it — the same scoping constraint stated at the top of this paragraph, seen from the other side. `DotLabel` therefore accepts only width-invariant utilities, and the tier-dependent size of the rows it sits in is set on a consumer-owned ancestor (`.exp-head`, `.blog-meta`) and inherited in.

## Styling policy

One invariant carries the whole styling system:

> Markup classes are width-invariant Tailwind utilities only. Every property that changes across responsive tiers lives in the component's scoped `<style>`, written as plain range media queries — unless the whole rule is system-owned in `global.css` (the shared section rhythm below), in which case its tier steps live there with it.

A fluid `clamp()` counts as changing across tiers, even though it names no breakpoint: `404.astro`'s display heading is a scoped `.notfound-title` rule for the same reason `Hero`'s is a scoped `.hero-title` rule, rather than a `text-[clamp(…)]` utility in markup. Pages are held to the invariant as firmly as components — a page with no scoped block would otherwise be a carve-out nobody declared.

The invariant holds for the chrome as well as the sections — `Header` and `ThemeToggle` earn no carve-out, since two policies would be the real smell. It has exactly one exception, and it is about the utility rather than the component: a variant may stay in markup when the utility it modifies is a bundle with no single-declaration equivalent. `sr-only` is the only such utility in play (nine declarations; hand-copying them into a scoped block is worse, and `@apply` there would need a `@reference` import of `global.css`), and it has two uses: `ThemeToggle`'s phone-sm-tier label, which is the responsive case, and the skip link's `focus:not-sr-only`, which is the state case. Everything else — a gap, a padding, a font size, a `flex-wrap` — is one declaration and moves. The skip link shows where the boundary sits: the reveal is a markup variant because it toggles the bundle, while the positioning that keeps the revealed link out of the header's flow is a single declaration, so it lives in the scoped block (and wins, because component styles are unlayered while Tailwind's utilities are layered).

Inside a scoped block, a unique semantic element is selected by its tag (`header`, `nav`, `nav a`, ThemeToggle's `button`) and only non-semantic wrappers earn a class (`.header-actions`, `.exp-head`, `.blog-meta`, `.intro-aside`). Astro scopes every rule to its own component, so a tag selector can't reach past the file that wrote it.

State follows the same split: single-element state stays in markup as variants (Experience's `hover:border-accent-text`), while relational state — a parent's hover driving descendants, like Blog's rows — lives in the scoped `<style>`, where utilities could only express it by adding `group` plumbing to the markup.

Two facts force this split:

- Astro's scoped-style compiler does not process selectors inside Tailwind `@variant` blocks — rules there lose their scoping attribute and `:global()` is left unstripped — so scoped styles cannot use Tailwind's responsive variants.
- The breakpoint tokens in `global.css` compile to strict `width <` media queries, so the scoped blocks use the same range syntax (`(width < 900px)`, `(700px <= width < 900px)`) to keep both halves of the system agreeing at the boundary.

Design tokens are defined once in `global.css` and exposed as Tailwind utilities via `@theme inline` (values and roles are tabled in [design.md](design.md)). The two repeated type sizes are tokens on the same footing: `--text-meta` (13px — nav, cues, CTAs, labels) and `--text-body` (15px body copy at its base tier — the Hero blurb, the shared section intro's blurb, Experience descriptions, Blog's date/read-time column and its excerpt, and the 404 paragraph), used as `text-meta`/`text-body` in markup and as `var(…)` for the base tier in scoped styles. Their block is `@theme static`, and the keyword is load-bearing: Tailwind emits a theme variable only where it sees the utility used and never scans Astro's scoped `<style>` blocks, so without it those `var()` references would break the day the last markup use went away — silently, as an inherited font-size rather than an error. Tier steps off those bases stay literal, because they are tier values rather than tokens. The scale stops there by decision, not omission: each token names one recurring role, while the remaining repeated size (11px — intro eyebrows, Hero's rail label, the footer labels, Experience's pills) spans four roles with different tier behavior, so there is no single token to name. Defining the four tiers also exposes `max-laptop:`/`max-tablet:`/`max-phone:`/`max-phone-sm:` variants, but the invariant keeps width rules out of markup, so exactly one of them is used anywhere: `max-phone-sm:sr-only`, the one markup exception above. The other three stay as the named tier scale that the scoped media queries write out longhand, and no min-width or stacked variant survives; media-query literals in scoped styles carry a comment naming the tier they belong to, and name the tier rather than the token (a `--breakpoint-*` spelled inside an `.astro` file is a variable reference to Tailwind's scanner, which then emits the token whether or not any rule uses it).

Four layout primitives are system-owned in `global.css` rather than re-encoded per component: the responsive `--gutter` custom property (the shared section gutter — conditions can't read variables, but declarations can), the `section-screen` utility (a section's viewport-filling height under the header), the `section-list` utility (a section's evenly-distributed content list, inset by the gutter), and the `section-cue` utility (the flat-bottom scroll-cue rhythm for in-flow sections; an absolutely-positioned cue opts out).

## Theming

- Light is the default outright; dark is the `data-theme="dark"` attribute on `<html>`, and the only thing that sets it is a stored choice. The pre-paint script reads `localStorage` and applies dark if it finds it — nothing else. `prefers-color-scheme` is not consulted anywhere in the runtime: not on load, and not while the page is open, so a visitor's machine switching to dark at sunset leaves the site as they left it. That the CSS already agrees is why the attribute is set before first paint rather than by a media query: the token block is unconditional light and the dark block only overrides it. The one place the OS still shows through is `public/favicon.svg`, which carries its own `prefers-color-scheme` block — it renders in browser chrome rather than in the page, so it follows the chrome. `ThemeToggle`'s `applyTheme` remains the single place a flip touches the attribute, the `theme-color` meta and the fade class. The attribute name and storage key are constants in `lib/theme.ts`; `global.css` co-owns the values (its dark variant and token block hard-code the attribute), and both files say so.
- The theme-flip fade is temporal: `ThemeToggle` puts `.theme-switching` on the root only for the duration of a toggle, so the 500ms color transition runs exactly then — hovers stay instant and the first paint can't flash. `<html>` carries the `--bg` background as well as `body`, and the pair is deliberate despite reading as redundant: the root fills the canvas — what shows in the overscroll gutter — while `body` keeps its own so the page background is painted by a box. With both declared, the propagation a transparent root would trigger (`body`'s background used for the canvas, `body` itself then not painted) never happens, so the fade stops depending on how an engine treats a propagated background mid-transition. That is the asymmetry the iPhone flip pointed at, and it is not reproducible on the desktop engine the suite runs, so the arrangement is chosen to remove the variable rather than on a measurement of it. The root fades too, but on `background-color` alone: it declares no `color` of its own, and the one it inherits from the UA flips with `color-scheme`, so joining the main rule would animate a colour that renders no text.
- Reduced motion: everything opts out. Smooth anchor scrolling falls back to `auto` (a page-length scroll is large motion), and a blanket `*, ::before, ::after` rule collapses every transition — theme fade, read-more expand, nav highlight — to `0.01ms`. The duration is `0.01ms` rather than `0` on purpose: `transitionend` still fires, so the read-more's expand handler in `Experience.astro`, which waits on that event, keeps working instead of hanging.

## Client JavaScript

Behavior is colocated: each component carries its own `<script>`, which Astro bundles as a deferred module and dedupes across uses — scripts run once, after the document is parsed, with no ready-state wrappers. The one exception is deliberate: the theme init in `Base.astro` is `is:inline` because it must run before first paint.

| Script                | Responsibility                                                                                                                                                                                                                                   |
| :-------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Base.astro` (inline) | Before first paint: flag `<html>` with `data-js` for progressive enhancements to gate on, and apply a stored dark choice (light otherwise — the OS is never consulted)                                                                           |
| `Header.astro`        | Measure the header into `--headerH` (ResizeObserver); sync the active nav link on scroll, with a short lock on plain left clicks to hashes the nav owns so the highlight moves immediately                                                       |
| `ThemeToggle.astro`   | Flip `data-theme`, persist the choice, and run the temporal fade (duration read from the `--theme-fade` token, so CSS and cleanup timeout can't drift)                                                                                           |
| `Experience.astro`    | Read-more expand/collapse on the phone tier, animating through an explicit pixel height; and measure each description against the clamp, flagging `data-fits` on rows with nothing to reveal (re-run per frame on resize, and once fonts settle) |
| `Footer.astro`        | Measure the footer into `--footerH` (ResizeObserver), which Contact's screen-height formula subtracts                                                                                                                                            |

Each of these has a case in `tests/site.spec.ts` guarding the part of it a user would notice: the inline script by the `data-js`-gated read-more test and the console-error canary, `Header` by the `aria-current` test, `ThemeToggle` by the flip-and-persist test, `Experience` by the phone-viewport expand test. The two ResizeObserver measurements are asserted only indirectly, through the axe scan and the layout the other cases walk through — a height in a custom property has no user-visible contract to pin.

## Decisions

Choices a reviewer might question, and why they went this way:

- **`svh` for section heights** — equals `vh` on desktop and stays stable on mobile when the browser chrome collapses; `dvh` would resize sections mid-scroll.
- **`lh` for the read-more clamp** — `3lh` derives "three lines" from the element's real line-height instead of encoding it a second time; browsers below the unit's floor (older than the mask-image floor below) simply don't clamp.
- **`aria-current="location"` for the active nav link** — the semantically correct signal for "current place in the page", and the styling hook, in one attribute; a `data-` attribute would duplicate state assistive tech can't see.
- **Unprefixed `mask-image` only** — the build's CSS minifier strips `-webkit-` prefixes per its Baseline browser targets, so authoring them would be dead source; pre-Baseline browsers lose only a cosmetic fade, never the content clamp.
- **Design-file dead code is not ported** — the design's pill-balancing script (guard condition can never hold) and its 640px article rule (fully shadowed by a later block) are provably inert, so the implementation omits them rather than shipping code that never runs.
- **Blog rows are non-link `<article>`s** — the design marks them up as anchors, but their `href="#blog"` self-reference is a dead link: a focusable tab stop with no destination that would scroll-jump on click. The hover treatment stays — design fidelity carried ahead of the real links — but the design's pointer cursor does not: a pointer promises a click target that doesn't exist yet. The rows become real `<a>` links (and regain the cursor for free) when article pages exist.
- **Color literals that shadow tokens become tokens** — e.g. the design's hard-coded article hairline is `border-hair` here, so dark mode keeps a visible border.
- **`section-screen` is height-only** — the utility owns only the height formula; the page-width cap is the plain markup pair `mx-auto max-w-page`, carried by the header and each capped box (section roots, Contact's CTA and the footer's inner) rather than bundled into the utility. Both current consumers (`Hero` and `Section`) do carry the cap; keeping it out of the utility is what lets a full-bleed section take the screen height without also inheriting a width it doesn't want.
- **The footer is a `<main>` sibling with a measured height** — the design draws Contact's CTA and the site footer sharing the final screen, but a `<footer>` inside the section can't be a `contentinfo` landmark. So `Footer` sits after `<main>` and mirrors Header's measured-custom-property pattern (`--footerH`), and Contact's `contact-screen` subtracts both chrome heights to keep the pair filling one viewport. Without JS the fallback is `0px`: the CTA takes the full screen and the footer follows.
- **In-page links say ↓, external links say ↗** — the scroll cues jump within the page, so they carry ↓; ↗ is reserved for links that leave it (the footer's GitHub/LinkedIn, and every "Get in Touch" — `ContactCta` and Contact's button alike, which open a mail client), keeping the affordance vocabulary consistent.
- **Every "Get in Touch" is the `mailto:`, not a jump to `#contact`** — the CTA is the site's one conversion, and routing the header and section-intro copies through a scroll to the Contact section would have put a second click between reading and writing. They link straight to `mailto` (single-sourced in `lib/site.ts`, shared with the Contact button and the footer address), so the only in-page path to Contact is the nav link and the scroll cues. A side effect worth knowing: the CTA no longer matches Header's `a[href^="#"]` click handler, so it takes no part in the scroll-spy highlight lock. The Résumé row carries no arrow at all, matching Blog's non-link "Read article": it is a placeholder span, and ↗ would promise a destination that doesn't exist yet.
- **Footer contrast lifts are theme variables** — the footer inverts (`bg-ink` flips with the theme), so in dark mode 50%-opacity text sits on a light panel and falls to ~3.5:1. The dim levels are theme-conditional values, not element state, so they live with the other theme-conditional values in `global.css` (`--on-ink-dim`/`--on-ink-mid`, lifted in the dark block) and the markup consumes them as `opacity-(--var)` utilities.
- **Hover states get their own accent tokens** — `--accent-text` is tuned as text on `--bg`, which makes it _lighter_ than `--accent` in dark mode, so reusing it as the Contact button's hover background put white text at 3.08:1. Separately, `--accent` as text on the inverted footer panel is 3.18:1 light and 4.23:1 dark. Both are hover-only, and axe reads the resting state, so the scan passed either way while the resting states genuinely do pass. Hence `--accent-hover` (one value for both themes — the only red that clears 4.5:1 under white in each) and `--accent-on-ink` (theme-conditional, the opposite theme's accent), sitting beside `--on-ink-dim`/`--on-ink-mid` as contrast-tuned values rather than new palette entries.
- **`prefers-color-scheme` is not read at all** — the unusual half of the theme contract, and the one a reviewer will stop on. A dark machine gets a light site until its owner presses the toggle. The reasoning is that the OS setting is a preference about the _system_, and the site's own default is a design decision the design already made (light); inferring one from the other put visitors in a theme they never chose, and the live subscription that used to back it made the theme change under them mid-visit. So the toggle is the only input, and it persists. The cost is real and accepted: a visitor who prefers dark everywhere pays one tap, once per browser. This is also why `playwright.config.ts` states `colorScheme` rather than inheriting it — the emulated OS is the variable the dark-OS case holds constant while asserting a light page.
- **The theme fade is 500ms, not the design's ~260ms** — a deliberate deviation: the full-page flip reads better slowed down. The duration is single-sourced as `--theme-fade` in `global.css`; ThemeToggle's cleanup timeout derives from it. Slowing it down is also what made the background/text asymmetry on iOS visible in the first place, which is what led to `<html>` carrying the background alongside `body` — see the Theming section.
- **Tests are a smoke and a11y gate, not a unit suite** — the other gates (formatting, ESLint with `jsx-a11y`, strictest typecheck, build) are all static, so the four DOM scripts and the landmark structure could regress without anything noticing. `tests/site.spec.ts` covers the runtime behaviour a visitor would actually lose — no console errors on boot, the skip link as first tab stop, all four sections exposed as named regions, the theme flip persisting, `aria-current` following a nav click, the read-more expanding on the phone tier, and the 404 page answering with a 404, a `noindex` and no canonical — plus an axe scan in both themes, dark seeded before first paint so the scan can't catch the page mid-fade, and repeated at the phone viewport in both the collapsed and the expanded state, since the read-more's ARIA and ThemeToggle's `sr-only` label are live only below those tiers and the desktop scan has never seen them. The theme has three cases beyond the flip, because what it must do is ignore the OS on both of the paths that used to consult it, and stay usable anyway: a page opening light under a dark OS with nothing stored (the pre-paint script), the toggle still reaching dark from that same dark-OS page (the escape hatch that makes ignoring the OS defensible — deliberately overlapping the flip case, which runs under a light OS), and a live OS switch on an open page changing nothing (the absent listener). The last needs a positive to wait on before it can assert an absence — a `not.toHaveAttribute` passes on its first poll, potentially before the renderer has dispatched the media change at all — so it registers a marker listener of its own first and waits for that to fire. What it deliberately does not do is re-assert that a _stored_ choice survives an OS switch: the listener that was removed returned early on a stored choice, so a verbatim reintroduction would be invisible after a toggle click and is caught by the empty-storage case instead. All three are why `playwright.config.ts` states `colorScheme: "light"` rather than inheriting it: the emulated OS is the variable they hold constant, and the dark-OS block overrides it to assert both halves of the contract under a dark machine. The named-region case is not redundant with the scan: axe has no rule requiring a `<section>` to be named, so stripping every `aria-labelledby` leaves the scan clean (measured — the region count falls from four to zero while axe still reports zero violations). The emptiness check in that case is not redundant either: an `aria-labelledby` pointing at an _empty_ element leaves the section counted as a region, so only the check on the title element sees it. The read-more has three cases. Two of them assert the description actually grew, since it answers to `prefers-reduced-motion` as well as to the click, and both route through one helper so the technique has a single home: wait for the settled computed `max-height: none`, then measure. Deliberately not a poll — polling was tried twice and both attempts passed against a deliberately broken build, because the row animates _twice_, out to an inline pixel height and then back down to the clamp once that style is cleared, so any poll for "taller than before" catches one of those frames. State alone was not enough either: with the `[data-open]` max-height rule deleted, the click still sets an inline height, still flips `aria-expanded` and still swaps the label. The reduced-motion case guards the other half — the blanket transition override is `0.01ms` rather than `0` precisely so `transitionend` still fires and the inline height still gets cleared. The third case shortens a description in the page to reach `data-fits`, which no fixture can exercise, and asserts the row drops both its toggle and its fade and regains them when the text is restored. What is deliberately absent: component snapshots, which would pin markup no consumer depends on, and a cross-browser matrix — one engine catches script regressions, and browser-specific CSS is verified by hand against the design. Unit tests arrive with real logic to unit-test (article pages, forms).
- **The e2e suite previews on 4322, with `ASTRO_PREVIEW_BACKGROUND` set** — two unguessable details in `playwright.config.ts`. The port is 4322 rather than Astro's default 4321 because `astro dev` owns that one, and `reuseExistingServer` would otherwise silently run the whole suite against a dev server someone left running instead of against `dist/`. The environment variable is the fix for Astro detaching the preview server when it detects a coding agent started it: the launched process exits immediately and Playwright reports its `webServer` as having exited early. Astro sets the same variable on the child it spawns for `--background`, so setting it here means "the backgrounding decision is already made — be the server".
- **The underlined-CTA class string stays inline** — `border-b border-accent-text/40 pb-0.5 text-meta text-accent-text` repeats across a `<button>` (Experience's read-more), a `<span>` whose hover is driven by its parent row (Blog), and an `<a>` (404). Extracting it would mean a component that can't be one (three elements, three hover stories) or a custom utility, which buys four declarations at the price of a second vocabulary beside Tailwind. The type token already removes the only magic number in it.
- **The skip link's target carries no `tabindex="-1"`** — the conventional attribute is there to make a non-focusable `<main>` receive focus, and browsers stopped needing it: the sequential focus navigation starting point has shipped in Firefox, Chrome, Edge and Safari since 2013–2016, and current cross-browser testing of skip links without the attribute (four browsers, five screen readers) finds no failures. It is not free either — `tabindex="-1"` on a `<main>` can break the back button on iOS. So the attribute would buy a fixed problem at the price of a live one. Verified here: activating the link puts the next Tab on the first control inside `<main>`.
- **The theme init is duplicated rather than shared with `lib/theme.ts`** — the obvious cleanup is a `readTheme()`/`writeTheme()` pair in `lib/theme.ts`, and it can't be done. The init must beat the first paint, so it can't be a bundled module; that makes it `is:inline` (which `define:vars` implies anyway), and Astro renders inline scripts verbatim with no import resolution. So `readTheme()` would have exactly one possible caller, and it isn't the one that duplicates anything. What is genuinely shared — the storage key, the attribute name, the per-theme `--bg` values — already lives in `lib/theme.ts` and is passed in through `define:vars`; what is left is four lines of DOM code in two incompatible execution contexts. The alternative that would single-source it, exporting the script body as a template string and injecting it with `set:html`, trades type-checking, linting and formatting for that, on the one script that runs before everything else.
- **Progressive enhancement is gated on a root flag set before first paint** — the Experience read-more is CSS-clamped and JS-expanded, so on its own the clamp would trap the text for anyone with scripts blocked. The clamp and its toggle now hang off `html[data-js]`, which the pre-paint script sets: no JS means the descriptions render whole and the dead toggle never appears. The flag is set there rather than by `Experience`'s own script because a bundled module is deferred — it would paint the unclamped text and then snap it shut. One line in a script that has to exist anyway, against a component-owned flag that flashes.
- **A row whose description already fits drops the toggle _and_ the fade (`data-fits`)** — whether there is anything to reveal is a property of the rendered text, not of the content, so it is measured rather than assumed: `scrollHeight <= clientHeight` asks the clamp for its own answer instead of re-deriving the `3` that `max-height: 3lh` owns. There is no CSS-only form of the question inside the build's Baseline targets, and `html[data-js]` answers "did scripts run", not "does this text overflow". Three details are load-bearing. Open rows are skipped, because mid-expand the two heights agree and would read as "fits", hiding the control that closes the row again. The clamp stays _unconditional_ rather than scoping `max-height` to `:not([data-fits])`, which reads better and breaks the measurement: with the clamp lifted the two heights agree whatever the text says, so a row that once fit measures as fitting forever and never re-clamps when the viewport narrows (measured — the shipped description then renders at 117px against a 58.5px clamp). And the mask must be turned off with the button, not left behind: its ramp is measured from the box's own bottom, so on a box shorter than the clamp it fades most of a real final line and advertises content that isn't there. The measurement re-runs on resize, coalesced per frame like Header's nav sync, and once `document.fonts.ready` settles — a deferred module can measure the swap fallback, and across 24 lengths straddling the three-line boundary the verdict flips at two of them. That race is benign in this direction (Archivo is the narrower face, so a stale verdict leaves a button on a row that no longer needs one rather than hiding one a clamped row does), but it is one line to close.
- **The Résumé row is a non-link, and years are derived** — the design's Résumé row would be a dead `#` link (same rationale as the blog rows), so it's a literal span until a CV is hosted; both years the site shows (the footer's © line and Hero's rail label) come from build time rather than hard-coding the design's 2026.
